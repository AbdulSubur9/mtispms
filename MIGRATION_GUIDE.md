# Database Migration Guide — Code Review Update

This update changes the schema in ways that matter for any environment that
already has data (i.e. not a fresh `flask db upgrade` on an empty database).

## New tables

- `school_payment_types` — custom payment types per school (item 6)
- `attendance` — teacher attendance records (item 7)
- `student_applications` — admission/application forms (item 8)

These are pure additions; `flask db migrate` will generate `CREATE TABLE`
statements for them with no special handling needed.

## Changed columns — the critical one

`students.student_id`, `payments.receipt_number`, and
`expenses.reference_number` were previously declared **globally unique**
(`unique=True` on a single column). This was the root cause of the
"Internal Server Error on student/payment/expense creation for a second
school" bug: every school's generator independently counts from #0001, so
the second school's first insert of each type collided with the first
school's #0001 and failed with an `IntegrityError`.

They are now **composite-unique per school**:
`UniqueConstraint(school_id, student_id)` (and the equivalent for the other
two).

### If you're deploying fresh (empty database)

Nothing special — just run the normal migration flow:

```bash
flask db migrate -m "Composite unique constraints for multi-tenant IDs; add payment types, attendance, applications"
flask db upgrade
```

### If you already have production data with the OLD global-unique constraint

You need to drop the old single-column unique index/constraint before
Alembic can add the new composite one. Autogenerate usually detects this,
but verify the generated migration contains something equivalent to:

```python
def upgrade():
    # Drop the old (incorrect) single-column unique constraints
    op.drop_constraint('students_student_id_key', 'students', type_='unique')
    op.drop_constraint('payments_receipt_number_key', 'payments', type_='unique')
    op.drop_constraint('expenses_reference_number_key', 'expenses', type_='unique')

    # Add the new composite ones
    op.create_unique_constraint(
        'uq_students_school_student_id', 'students', ['school_id', 'student_id']
    )
    op.create_unique_constraint(
        'uq_payments_school_receipt_number', 'payments', ['school_id', 'receipt_number']
    )
    op.create_unique_constraint(
        'uq_expenses_school_reference_number', 'expenses', ['school_id', 'reference_number']
    )
```

(Exact constraint names depend on what PostgreSQL auto-named them; check
`\d students` in `psql` if the autogenerated migration doesn't find them
by the guessed name above.)

**Before running this in production:** if you have ever had more than one
school in the database, check for existing duplicate `(school_id,
student_id)` pairs first — there shouldn't be any (the bug prevented them
from ever being *created* in the first place), but it's worth a
one-off sanity query:

```sql
SELECT school_id, student_id, COUNT(*) FROM students
GROUP BY school_id, student_id HAVING COUNT(*) > 1;
```//same for payments.receipt_number and expenses.reference_number

If that returns rows, resolve them manually before the migration runs, or
the new unique constraint creation will fail.

## New foreign key

`payments.payment_type_id` → `school_payment_types.id` (nullable). Existing
payment rows are unaffected — they simply have `payment_type_id = NULL` and
keep using the legacy `payment_type` string column, which is unchanged.

## Recommended migration commands (fresh or dev environment)

```bash
source venv/bin/activate
flask db migrate -m "Multi-tenant fixes, payment types, attendance, applications"
# Review the generated file in migrations/versions/ before applying -
# especially the constraint-drop/create statements described above.
flask db upgrade
```
